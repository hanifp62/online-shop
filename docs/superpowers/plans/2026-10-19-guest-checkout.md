# Rencana Implementasi: Guest Checkout dan Pelacakan Aman

## Cakupan dan bukti

Rujukan: `docs/superpowers/specs/2026-10-19-guest-checkout-design.md`, R-34 / FR-034-01 sampai FR-034-07. Ini rencana, bukan perubahan aplikasi. `routes/web.php` menaruh `POST /checkout` di grup `auth`; `resources/views/shop/index.blade.php` menampilkan formulir checkout hanya saat login. Keranjang sudah tersimpan di sesi (`CheckoutService::cart`) dan dipakai oleh `/belanja`. `CheckoutService::checkout(User, Address, ...)` menangani replay, harga server, decrement stok bersyarat, transaksi dan retry lock. `orders.user_id` wajib; indeks unik `(user_id,idempotency_key)` tidak melindungi baris dengan `user_id=NULL`. `AdminOrderController::invoice()` mendereferensi `$order->user->name/email`; laporan sudah memakai null-safe, tetapi nama guest kini menjadi `-`.

## Keputusan aman dan batas kontrak

- Pertahankan `CheckoutService::checkout(User, Address, ...)` dan respons checkout akun. Tambahkan jalur guest yang menggunakan fungsi internal transaksi stok/harga/order-item yang sama; jangan menyalin algoritme decrement, retry, atau transition. Jangan ubah `config/security.php`, `tests/Feature/CspReportOnlyTest.php`, atau berkas kotor lain.
- Migrasi tambahan, bukan mengedit migrasi lama: `user_id` nullable dengan kebijakan foreign key lama diperiksa sebelum migrasi; tambahkan `customer_name`, `customer_email`, `customer_phone` snapshot, `guest_scope_hash` nullable, `tracking_token_hash` nullable dan `tracking_expires_at` nullable. Pertahankan indeks unik akun lama. Tambahkan indeks unik `(guest_scope_hash,idempotency_key)` untuk guest; semua guest harus memiliki scope non-null. Indeks unik `tracking_token_hash` untuk token yang ada. Uji kompatibilitas SQLite dan target MySQL/MariaDB, termasuk alter foreign key dan rollback; jangan jalankan migrasi destruktif pada data nyata. User deletion saat ini cascade menghapus order: putuskan retensi historis sebelum mengubah FK; opsi aman `nullOnDelete` bila retensi disetujui, migrasikan FK secara hati-hati.
- Scope guest: buat nilai acak server-side berentropi tinggi satu kali per sesi, simpan hanya di sesi; simpan SHA-256 scope pada order. Jangan gunakan IP/email/session ID mentah sebagai scope. Pisahkan namespace guest dari akun dengan lookup `whereNull('user_id')->where('guest_scope_hash', ...)`; akun tetap memakai user ID. Bind replay ke payload terkanonisasi (kontak, alamat, voucher, item), bukan hanya `address_id`; bedakan perubahan payload dengan `409` tanpa mutasi. Pertahankan kunci checkout pada klien sampai hasil definitif; jangan menghasilkan kunci baru setelah respons jaringan hilang.
- Voucher guest **ditolak eksplisit** (`422`) sebelum transaksi atau replay; kuota per-user tidak boleh dibypass. Tarif ongkir saat ini nol dan pembayaran belum tersedia; tampilkan status `pending / belum dibayar`, jangan menjanjikan pembayaran atau pengiriman otomatis.
- Token tracking: `random_bytes(32)` atau setara, hash SHA-256 di DB, expiry eksplisit, token mentah hanya pada respons sukses pertama. `Cache-Control: no-store`; tidak ada token di route path/query, redirect, HTML publik, referer, telemetry, atau log. `GET /orders/track` hanya formulir tanpa token; `POST /orders/track` menerima token di body melalui CSRF, rate-limit IP + fingerprint hash token, mengembalikan proyeksi data minimal, bukan serialisasi model. Invalid/expired sebaiknya respons seragam agar tidak menjadi oracle. Jangan dukung lookup nomor order publik.
- Kehilangan respons pertama menciptakan masalah: hash token saja tidak memungkinkan mengembalikan token pada retry. Pilihan aman: sesi menyimpan token mentah sementara, terikat scope dan idempotency key, dengan TTL pendek serta tanpa logging; retry identik mengembalikan token yang sama hanya selama sesi masih valid. Hapus setelah TTL, bukan segera setelah checkout. Jika sesi hilang, jangan mint token kedua hanya dengan order ID/email; tampilkan jalur bantuan manual atau kanal konfirmasi tepercaya yang sudah tersedia setelah diverifikasi. Uji pemulihan dan kehilangan sesi.

## Checklist bertahap

### 1. Skema dan model (FR-034-01/02/03/04/06)
- [ ] `database/migrations/<timestamp>_add_guest_checkout_to_orders_table.php`: tambah kolom dan indeks di atas, inspeksi FK `user_id` dan migrasi aman; uji uniqueness guest termasuk dua sesi dan indeks akun lama. Risiko tinggi: DB produksi dan FK lintas driver.
- [ ] `app/Models/Order.php`: fillable/casts hanya untuk kolom baru; jangan sertakan hash/token dalam JSON order publik. Pertimbangkan penyembunyian `payload_hash`, `guest_scope_hash`, `tracking_token_hash`, snapshot PII dari respons umum. Risiko sedang: kontrak JSON akun.

### 2. Transaksi checkout (FR-034-01/02/03/06)
- [ ] `app/Services/CheckoutService.php`: ekstrak bagian bersama *setelah* validasi identitas/snapshot untuk penetapan harga, decrement stok, pembuatan item, retry dan penanganan unique collision. Jangan ubah signature akun yang dipakai `OrderController` dan tes refleksi `place()` di `AmadisOrderTest`. Guest lookup sebelum dan di dalam transaksi; unique violation harus mencari ulang berdasarkan scope+key, lalu validasi hash. Jangan menganggap setiap SQLite error 19 sebagai collision idempotensi tanpa lookup. Risiko tinggi: double stock, deadlock, replay.
- [ ] `app/Http/Controllers/OrderController.php` atau controller guest kecil baru, `routes/web.php`: `GET /checkout` publik dan `POST /checkout` publik dengan dispatch eksplisit berdasarkan auth/mode. Akun tetap wajib alamat miliknya; guest tidak boleh mengirim `address_id`, `user_id`, harga, status, atau voucher. Validasi nama, email, telepon, field alamat mengikuti `app/Http/Controllers/AddressController.php` / `app/Models/Address.php`; normalisasi email dan kontak sebelum hash dan simpan snapshot alamat setara `Address::snapshot()`. Gunakan CSRF web middleware, `throttle:checkout`, validasi cart server, kosongkan cart hanya setelah commit berhasil. Risiko sedang: login/session beralih saat retry.
- [ ] Pertahankan `OrderController::index/show/cancel` tetap auth + filter `user_id`; jangan izinkan guest melewati `ReviewController` atau `AddressController`. Audit seluruh akses order dari route publik. Risiko tinggi: IDOR.

### 3. Tracking dan pemulihan (FR-034-03/04/05)
- [ ] Controller tracking baru di `app/Http/Controllers/`, route di `routes/web.php`, view aman di `resources/views/shop/`: `GET` formulir kosong, `POST` token body. Lookup hash + expiry; rate limit dengan kunci terbatas dan hash fingerprint, tidak mencatat input. Hasil hanya nomor referensi, status, item, total, waktu, tujuan tersamarkan; jangan keluarkan email/telepon lengkap, alamat lengkap, token atau relasi `user`. Set no-store pada sukses/gagal. Risiko tinggi: kebocoran capability token dan PII.
- [ ] Buat token pada pembuatan order guest di transaksi yang sama dengan hash/expiry; buat mekanisme replay token sesi ber-TTL di jalur guest. Pastikan respons JSON sukses pertama dan replay identik membawa token selama sesi sah, beda payload `409`, sesi hilang tidak mengungkapkan order. Risiko tinggi: hasil commit hilang saat jaringan putus.

### 4. UI dan admin (FR-034-01/05/06/07)
- [ ] `resources/views/shop/index.blade.php`: gunakan cart sesi dan helper `api()` yang ada. Guest dapat checkout tanpa login, maksimum tiga tahap: kontak/alamat, ringkasan+konfirmasi, hasil. Ringkasan item, diskon (0 bagi guest), ongkir, total, penerima selalu tampak pada desktop/mobile; server tetap sumber harga. Pertahankan checkout akun, desain ZAFIRA, label jelas, fokus/error dan target sentuh 44px. Simpan idempotency key ketika timeout; jangan tampilkan token di URL atau HTML halaman yang dapat di-cache. Uji respons jaringan hilang dan instruksi lanjut manual bila sesi hilang. Risiko sedang: regresi tampilan dan stale totals.
- [ ] `app/Http/Controllers/AdminOrderController.php`: invoice gunakan snapshot nama/email untuk guest, fallback user untuk akun; escape semua teks. Laporan gunakan snapshot nama guest, tetap eager load user dan total/status benar. Admin index/show audit akses PII tetap hanya guard admin+TOTP. Risiko sedang: null dereference/XSS.

## Verifikasi (tulis tes RED sebelum tiap tahap, lalu GREEN)

- `tests/Feature/GuestCheckoutTest.php`: guest membuat satu order tanpa user; snapshot kontak/alamat; cart sesi tidak mengubah harga; input hilang/invalid, cart kosong, stok kurang, produk nonaktif dan voucher guest gagal tanpa order/decrement; kunci sama replay setelah cart dikosongkan tanpa stok ganda; payload berbeda 409; dua sesi memakai kunci sama menghasilkan dua order; concurrency satu sesi menghasilkan satu order melalui indeks, termasuk SQLite retry dan target MySQL bila tersedia.
- `tests/Feature/GuestTrackingTest.php`: hash bukan token mentah, expiry, invalid/expired tanpa oracle, POST body saja, GET query token tidak bekerja, rate limit, header no-store, tidak ada PII lengkap, order ID saja gagal, sesi lain tidak mendapat token replay, kehilangan respons pada sesi asli berhasil dipulihkan sebelum TTL, kehilangan sesi gagal aman.
- Perluas `tests/Feature/AmadisOrderTest.php`, `tests/Feature/MysqlCheckoutRetryTest.php`, `tests/Feature/AdminOrderReportTest.php`: pastikan akun tetap replay, kuota voucher, rollback stok, cancel sekali, invoice guest tidak crash/ter-escape, laporan akun+guest, endpoint order akun tidak membaca guest. Jangan melemahkan tes lama untuk menyesuaikan refactor.
- Browser manual/Playwright: `/belanja` desktop dan mobile, guest tanpa login → ringkasan terlihat → checkout pending → token hanya di respons/form pascaaksi → tracking via POST → invalid/expired; navigasi akun tetap baik. Periksa keyboard, screen reader labels, 44px, console/network, tidak ada token pada URL/log. Jalankan suite PHPUnit SQLite, tes MySQL opsional sesuai lingkungan, `npm run build`; bandingkan baseline sebelum dan setelah.

## Ketidakjelasan dan keputusan sebelum coding

1. Spec menyebut `GET /orders/track` menerima token, tetapi larangan token di URL mensyaratkan POST body. Pilih GET formulir kosong + POST lookup; perbarui spec saat implementasi disetujui.
2. Spec hanya menjamin token sekali dalam respons pertama, tetapi retry setelah respons hilang memerlukan token yang sama. Pilih cache sesi singkat terikat scope/key; nilai TTL dan masa berlaku tracking perlu ditetapkan (usul TTL replay 30 menit, tracking 30 hari). Kanal email konfirmasi order belum terbukti tersedia; jangan mengklaim recovery lintas sesi.
3. Migrasi FK `user_id` saat ini `cascadeOnDelete`; keputusan retensi order setelah penghapusan akun perlu persetujuan data sebelum deploy. Jangan ubah cascade diam-diam.
4. Format respons akun saat ini mengembalikan model Order penuh. Batasi perubahan serialisasi akun pada data sensitif baru; uji kontrak konsumen sebelum menyembunyikan field historis.
